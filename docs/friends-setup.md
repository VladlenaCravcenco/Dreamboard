# Друзья и личные списки желаний

## Подключение

1. В Supabase проекта `tbtzzpnshhsmpvyjjiyf` открыть SQL Editor → New query.
2. Выполнить весь файл `supabase/migrations/20261102010000_private_wishlists.sql` один раз. Он создаёт четыре новые таблицы и функции; существующие мечты не меняет. Для проекта с миграциями CLI применить обычным `supabase db push`.
3. Затем выполнить `supabase/migrations/20261102020000_gift_planning.sql` один раз: детали желаний, приоритеты, брони, личные планы и предпочтения. Если первая миграция уже выполнена, повторять её не нужно.
4. Опубликовать код вместе с `vercel.json`: GitHub → Vercel. Этот файл нужен для прямого открытия `/invite/<token>` и `/friends/<id>`.
5. Supabase Site URL: `https://dreamboard-three.vercel.app/`. Разрешить этот же URL в Redirect URLs. Google-вход возвращается на корень; приглашение хранится в sessionStorage и открывается после входа в той же вкладке. Для подтверждения почты в другой вкладке открыть исходную ссылку повторно после входа.
6. Проверить на двух аккаунтах: A включает свою ссылку; B открывает её, сохраняет A и отмечает желание; A не видит отметку. Повторить в обратную сторону. Изменение выбранной мечты A появляется у B при обновлении или в течение 15 секунд активной вкладки.

До применения миграции раздел показывает сообщение об отсутствующем обновлении базы. Код сам не создаёт таблицы и не открывает доступ к существующим желаниям.

## Поведение

- Друзья → Моя ссылка: имя для друзей, включение доступа, выбор конкретных желаний либо всех текущих и будущих. Доступ по умолчанию выключен.
- Ссылка — случайный UUID. Нет каталога пользователей или поиска. Любой получатель ссылки после входа может сохранить список; её можно переслать, поэтому это не индивидуальное приглашение по email.
- Друзья сначала отображаются карточками. Сохранение одностороннее: чтобы обменяться списками, каждый отправляет свою ссылку.
- Видны имя, название/категория/фото/описание/бюджет активных желаний, детали подарка, приоритет и добровольно заполненные предпочтения. Не передаются email, накопления, задачи, личные заметки, воспоминания.
- «Хочу подарить» — приватная отметка текущего пользователя. Это не бронь. «Я подарю» отдельно резервирует желание: другим друзьям видно только «занято», владелец не видит бронь или дарителя. Уникальный ключ в базе исключает две брони одного желания.
- Завершённые, удалённые или исключённые из доступа желания не показываются. Отключение доступа действует для ссылок и сохранённых друзей. Повторное включение восстанавливает прежний доступ.
- Замена ссылки отзывает старую ссылку, сохранённые связи и связанные отметки, заметки и брони. Друзьям нужно отправить новую ссылку.
- Изменения подтягиваются раз в 15 секунд в активной вкладке и при возврате к ней. Это polling, не Supabase Realtime.

## Проверки

`npm test` и `npm run build`.

`tests/wishlist-security.mjs` запускает реальную SQL-миграцию в PGlite (PostgreSQL WASM) с тремя пользователями и ролями Supabase. Проверяет владение выбранными мечтами, отсутствие лишних полей, недоступность таблиц напрямую, личные отметки, сохранённый доступ, отключение, замену ссылки и запрет anonymous RPC.

Пример установки тестового движка вне проекта:

```sh
npm install --prefix /tmp/dreamboard-db-test @electric-sql/pglite
PGLITE_MODULE=/tmp/dreamboard-db-test/node_modules/@electric-sql/pglite/dist/index.js node tests/wishlist-security.mjs
```

Изолированная UI-демонстрация: `node tests/build-preview.mjs`. Приглашение в тестовом сервере: `/invite/40000000-0000-0000-0000-000000000001`. Данные демонстрации находятся только в QA-адаптере; он не входит в production build.

## Новые возможности

- В форме новой мечты раскрыть «Добавить по ссылке на товар». После получения превью явно подтвердить использование названия и фотографии. Если магазин блокирует загрузку, ссылка сохраняется, а название и фото можно добавить вручную.
- Автозаполнение использует `api/product-preview.js` на Vercel. Обычный `npm run dev` запускает только клиент; серверный импорт проверять на Vercel или через Vercel dev. Дополнительные секретные ключи не нужны. Функция проверяет пользовательскую сессию, HTTPS и публичность адресов, ограничивает время и объём загрузки. Cookies пользователя в магазин не передаются.
- В карточке своей мечты — размер, цвет, ссылка, «можно похожее», «особенно хочу». Максимум три активных приоритета проверяются в базе; у друзей они идут первыми.
- Друзья → Моя ссылка → Подсказки для близких: интересы, цвета, нежелательные подарки, согласие на сюрприз и ближайший повод с датой. У друзей есть список ближайших поводов; уведомления пока не отправляются.
- В карточке друга — секретная заметка и этап «Идея / Заказано / Готово к подарку». Снятие личной отметки сохраняет план; отмена брони отдельная. Удаление друга удаляет его планы и освобождает брони.
- При временном исключении желания из доступа его бронь сохраняется и снова видна после возвращения желания. Завершённые желания не видны друзьям.

Перед публикацией проверить на трёх аккаунтах: A — владелец, B и C — друзья. B бронирует; C видит только занято и не может занять повторно; A не видит ни брони, ни заметок. После отмены B подарок доступен C. Проверить URL товара, предпочтения и ближайший повод после перезагрузки.

Локальные проверки включают SQL для трёх пользователей, исключительность брони, отсутствие чужих заметок, запрет прямого доступа к таблицам и служебной функции, лимит трёх приоритетов. Живой OAuth и импорт из конкретного магазина требуют проверки на опубликованном сайте.

Серверная функция и маршрутизация настроены по [документации Vercel для Vite](https://vercel.com/docs/frameworks/frontend/vite).

## Дни рождения и лента друзей

После предыдущих миграций выполнить `supabase/migrations/20261103010000_birthdays.sql` один раз и опубликовать код.

Профиль → День рождения: необязательные день и месяц, без года. Видимость по умолчанию выключена. Сохранение доступно даже до создания ссылки. Дата доступна только людям, сохранившим включённый список владельца; прямой доступ к таблице и служебной функции запрещён. Очистить дату → Сохранить удаляет её. Отключение видимости или ссылки убирает дату из следующих ответов API.

Друзья: сверху горизонтальная лента контактов, ниже календарь ближайших поводов. День рождения повторяется каждый год, 29 февраля в невисокосный год отображается как повод 28 февраля (это объяснено в профиле). Другие поводы остаются событиями с конкретной датой. Уведомления не отправляются. Уже увиденную человеком дату отозвать из его памяти невозможно.

Проверки: `npm test` покрывает смену года, сегодняшний день, 29 февраля, сортировку событий. SQL-тест покрывает закрытые даты, показ только сохранённым друзьям, отключение доступа и удаление даты.
